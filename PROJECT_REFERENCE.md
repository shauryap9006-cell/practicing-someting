## 1. Executive Summary

### Core Purpose

**RailTwin-X** is a real-time Indian railway delay prediction and network operations intelligence platform, built for **SIH 2026 Problem Statement PS 26028**. It is a full-stack system combining machine learning, a mechanistic physics-based simulator, a safety enforcement layer, and a REST API dashboard backend.

The system answers one central question in **advisory mode** (never autonomous):

> *"Given that train `#12301` is currently running 47 minutes late at Kanpur, what delay will it have when it reaches Allahabad Junction, with what confidence?"*

The system also provides causal delay attribution ("why was the train late?"), platform conflict resolution, crew duty breach alerts, and what-if cascade simulation.

**Advisory-only guarantee:** Every output carries `human_ack_required: True`. The system never issues autonomous control commands.

### Primary Input → Expected Output

| Input | Output |
|---|---|
| Train number + target station code | `[p10, p50, p90]` delay band in minutes |
| Real-time station event stream (live or mock) | Calibrated arrival time window: `best / likely / worst` |
| Network state query | All-train status with color coding (green/amber/red) |
| What-if shock (train, station, injected delay) | Cascade ripple across network with exact causal ledger |

## 4. Data Pipeline

### 4.1 Database Schema (SQLite — `data/schema.sql`)

11 tables form the operational data model:

| Table | Purpose |
|---|---|
| `stations` | Master station list (code, name, lat/lon, is_junction, platforms) |
| `trains` | 150 trains with class (rajdhani/shatabdi/superfast/mail/passenger) and priority (1–4) |
| `route_stations` | Ordered stop sequences per train with scheduled times and distances |
| `sections` | Corridor graph edges with distance, single-line flag, max speed |
| `rake_links` | Same physical rake turnaround links between train pairs |
| `station_events` | **Core training data** — historical and live arrival/departure events with delay in minutes |
| `weather` | Daily weather per station (temp, precip_mm, fog_flag) |
| `sim_ledger` | Exact causal delay breakdown from CascadeSimulator |
| `speed_restrictions` | Active Temporary Speed Restrictions (TSRs) |
| `live_ingest_events` | Append-only raw ingest log |
| `brain_advisory_audit` | Append-only audit log for every BrainOrchestrator advisory call |

### 4.2 Data Collection — `collector/collect.py`

The `DataCollector` runs a **3-tier failover adapter chain** per train:

```
Tier 1: RapidAPISource     → Live Indian Railways API (requires RAPIDAPI_KEY env var)
Tier 2: ScrapeSource       → Web scraping fallback
Tier 3: MockReplaySource   → Guaranteed synthetic data replayed from SQLite DB
```

Each collected batch goes through `QualityGate.validate_events()`:
- **Delay bounds:** quarantines if `delay_arr_min > 600` or `delay_arr_min < -120`
- **Stale events:** discards events older than 24 hours
- **Dead trains:** flags trains with no events for 3+ consecutive days

Valid events are idempotently upserted via `INSERT OR REPLACE` into `station_events`.

Weather is synced from **Open-Meteo API** for corridor stations and fog/rain flags are derived using:
- `fog_flag = 1` if `temp < 18°C AND humidity > 85%`
- `heavy_rain = 1` if `precip_mm > 25`

### 4.3 Feature Extraction — `ml/snapshots.py` + `ml/features.py`

The `SnapshotGenerator.build_dataset()` iterates all `(train_no, run_date)` pairs in the date range, and for every `(current_station k → target_station j)` combination generates a **23-dimensional feature vector** (`TrainFeatureVector`).

**Leakage Safety:** Historical statistics (F9, F10, F17) are computed **strictly on TRAIN period dates** (`compute_train_period_statistics(train_cutoff_date)`) and never include any future test dates.

|---|---|

### 4.4 Sequence Dataset for GRU — `ml/seq_dataset.py`

`SequenceDatasetBuilder.build_dataset()` constructs **3D tensors** of shape `[N, seq_len=8, feat_dim=8]`:

- Groups events by `(train_no, run_date)` into trajectories
- For each station index `t`, constructs the **last 8 preceding stations** as history
- Zero-pads shorter histories to `seq_len=8`
- Per-step features: `[delay_arr, delay_dep, halt_min, distance_km, is_junction, priority, sched_hour, dwell_delta]`

## 5. Model Architecture

### 5.1 Champion Model: `NonCrossingGRUQuantileModel` (PyTorch)

**File:** `ml/model_seq.py`

```
Input shape: [batch_size, seq_len=8, input_dim=8]
│
└── GRU(input=8, hidden=128, num_layers=2, dropout=0.2, batch_first=True)
    └── last_hidden = out[:, -1, :]                    # [batch, 128]
        │
        └── fc_shared: Linear(128→64) → ReLU → Dropout(0.2)
            │
            ├── head_q10:       Linear(64→1) ────────────────────── q10
            ├── head_delta_q50: Linear(64→1) → softplus → + q10 ── q50
            └── head_delta_q90: Linear(64→1) → softplus → + q50 ── q90

Output: (q10, q50, q90) — mathematically guaranteed non-crossing (softplus enforces positivity of deltas)
```

**Non-crossing guarantee:** `q50 = q10 + softplus(Δ₁)`, `q90 = q50 + softplus(Δ₂)`, ensuring `q10 ≤ q50 ≤ q90` by construction.

**Training:** Adam optimizer, `lr=0.002`, `weight_decay=1e-4`, 15 epochs, batch size 64.

**Loss:** `PinballQuantileLoss` — sum of pinball losses for α ∈ {0.10, 0.50, 0.90}:

```
L(q, α) = mean(max(α·err, (α-1)·err))
```

### 5.2 Quantile Estimators: LightGBM Quantile Ensemble (6 Boosters)

**File:** `ml/train.py` — `ModelTrainer.train_quantile_model()`

Six separate LightGBM boosters are trained with **pinball quantile loss**:

| Model Name | Objective | Alpha | Use Case |
|---|---|---|---|
| `model_direct_q10.txt` | `quantile` | 0.10 | Lower bound — ≤ 3 hops |
| `model_direct_q50.txt` | `quantile` | 0.50 | Point estimate — ≤ 3 hops |
| `model_direct_q90.txt` | `quantile` | 0.90 | Upper bound — ≤ 3 hops |
| `model_delta_q10.txt` | `quantile` | 0.10 | Per-section delta — > 3 hops |
| `model_delta_q50.txt` | `quantile` | 0.50 | Per-section delta — > 3 hops |
| `model_delta_q90.txt` | `quantile` | 0.90 | Per-section delta — > 3 hops |

**Routing logic:**
- `hops_remaining ≤ DIRECT_MODEL_MAX_HOPS (3)` → Direct models predict `target_direct_delay` directly
- `hops_remaining > 3` → Delta models predict per-section delay change; final prediction = `current_delay + (delta * hops)`

**LightGBM Hyperparameters** (from `config.py`):

```python
objective       = "quantile"
num_leaves      = 63
learning_rate   = 0.05
n_estimators    = 600     # num_boost_round
min_child_samples = 40
subsample       = 0.8
colsample_bytree = 0.8
force_col_wise  = True
```

**Input:** `pd.DataFrame` with columns matching `FEATURE_NAMES` (23 columns)  
**Output:** Single float prediction per row (delay in minutes)

### 5.3 Ensemble — `ml/ensemble.py`

**File:** `ml/ensemble.py` — `EnsemblePredictor`

Weighted linear blend of champion and challenger predictions:

```
p10_ens = 0.6 × q10_gbm + 0.4 × q10_gru
p50_ens = 0.6 × q50_gbm + 0.4 × q50_gru
p90_ens = 0.6 × q90_gbm + 0.4 × q90_gru
```

Falls back to LightGBM-only if GRU weights are unavailable or seq_tensor is not provided.

### 5.4 Conformal Calibration (CQR)

**File:** `ml/train.py` — `ModelTrainer.compute_conformal_calibration()`

Split-Conformal Quantile Regression adjustment is applied to the calibration tail (last 20% of training data):

```
Non-conformity score: s_i = max(Q_lo(x_i) - y_i, y_i - Q_hi(x_i))
q_hat = ⌈(n+1)(1-α)⌉/n quantile of {s_i}
```

At inference time:
```
calibrated_p10 = Q_lo(x) - q_hat
calibrated_p90 = Q_hi(x) + q_hat
```

Target coverage: **80%** (`CONFORMAL_MISCOVERAGE_ALPHA = 0.2`)

## 6. Training & Evaluation Loop

### 6.1 Data Splitting

**File:** `ml/train.py` — `ModelTrainer.prepare_datasets()`

A strict **time-based chronological split** is used — never random:

```
Total data range: [min_date, max_date] from station_events

TRAIN period = [min_date, train_cutoff]           (~80% of all days)
CALIB tail   = last 20% of train rows (row index)  (for CQR calibration)
TEST period  = [test_start, max_date]              (~20% or 7 days, whichever is smaller)

Training further filters:
  - direct_train: rows where hops_remaining <= 3 (for Direct models)
  - All rows used for Delta models
```

The split dates are recorded in `ml/artifacts/manifest.json` and reused identically during evaluation.

### 6.2 Loss Functions

| Model | Loss |
|---|---|
| LightGBM (6 boosters) | Pinball Quantile Loss (native `objective="quantile"`) |
| PyTorch GRU | `PinballQuantileLoss` — sum over α ∈ {0.1, 0.5, 0.9} |

### 6.3 Optimizer & Scheduler (GRU)

- **Optimizer:** Adam (`lr=0.002`, `weight_decay=1e-4`)
- **No LR scheduler** is present in the GRU training loop.
- **No early stopping** is implemented.
- **No gradient clipping** is implemented.
- **No Mixed Precision (AMP)** is used.

### 6.4 Evaluation Metrics — `ml/evaluate.py`

Computed on the held-out test week across 3 spatial horizons:

| Horizon | Distance Proxy |
|---|---|
| 1h horizon | km_remaining ≤ 90 km |
| 3h horizon | 90 < km_remaining ≤ 250 km |
| 6h horizon | km_remaining > 250 km |

**Metrics per horizon:**

| Metric | Description |
|---|---|
| `MAE (minutes)` | Mean Absolute Error of p50 prediction vs actual delay |
| `HitRate (≤10m)` | % of predictions within 10 minutes of actual |
| `80% Band Coverage` | % of actual delays falling within `[p10 - q_hat, p90 + q_hat]` |
| `Improvement vs B2` | % MAE improvement over official Indian Railways baseline |

**Baseline comparisons:**
- **B1 (Frozen Delay):** prediction = `current_delay` (no model)
- **B2 (Official Formula):** prediction = `max(0, current_delay - km_remaining / 30.0)`

**Hostile audit metrics (`ml/audit.py`):**
- `RMSE`, `R²`, `MAPE`
- 5-Fold Cross-Validation stability (MAE ± std)
- Overfitting gap: train MAE vs test MAE (flag if gap > 4 min)
- Data leakage patrol: flags features with `|correlation| > 0.95` with target
- Latency benchmark: 1,000 single-row inference runs (p50/p90/p99 in ms)
- Batch throughput at sizes 1/8/32/128

### 6.5 Promotion Gate — `ml/ensemble.py`

The GRU challenger is only promoted to champion if **all three conditions** are met:
1. MAE improvement over LightGBM champion ≥ **3%**
2. 80% coverage ≥ **75%**
3. Per-sample inference latency < **20 ms**

Results are written to `ml/artifacts/registry.json`.

### 7.2 Three-Tier Prediction Service — `api/predictor.py`

Every ETA prediction attempt follows an automatic **zero-fail fallback chain**:

```
TIER 2 — LightGBM Quantile + CQR Calibration (preferred)
  │   Requires: model files in ml/artifacts/ + live station_events
  ↓ (failure → falls through)
TIER 1 — Historical DB Lookup
  │   p50 = 0.4 × current_delay + 0.6 × historical_avg_delay_at_station
  │   Requires: at least some historical station_events in DB
  ↓ (failure → falls through)
TIER 0 — Fallback (Schedule + Current Delay)
      p50 = current_delay, p10 = max(0, p50-5), p90 = p50+15
```

The `tier_used` field in every response indicates which tier was applied.

### 7.3 Safety Interlock — `safety/interlock.py`

Every prediction (regardless of tier) passes through 5 **100% deterministic, zero-ML** safety checks before being served:

| Check | Rule |
|---|---|
| `input_sanity` | Required features present, finite, delay ≥ -30, km ≥ 0 |
| `quantile_order` | Enforces `p10 ≤ p50 ≤ p90`, caps width at 180 minutes |
| `recovery_feasibility` | Max delay reduction ≤ `dist_km / 10 + 5` minutes (kinematic limit) |
| `delay_bounds` | Hard clamp: predictions must be in `[-5, 720]` minutes |
| `monotonic_horizon` | Horizon drift ≤ 720 minutes from current delay |

If **any** check fails: prediction is clamped, `confidence_tier` is downgraded to `"LOW"`, and `verify_with_controller: true` is set.

### 7.4 Brain Orchestrator — `api/brain.py`

Full advisory pipeline triggered by `POST /v1/advise`:

```
1. State Perception: query latest station_events for train
2. Feature Extraction: SnapshotGenerator.extract_features_at_snapshot()
3. Ensemble Inference: EnsemblePredictor.predict()
4. Safety Interlock: validate_prediction_through_interlock()
5. Conflict Scan: ConflictScanner.scan_train_conflicts()
6. Action Formulation: advisory recommendations (never autonomous commands)
7. Audit Logging: append-only insert to brain_advisory_audit table
```

Returns `advisory_recommendations` with `human_ack_required: True` invariant enforced.

### 7.6 Post-Processing Steps

After raw model output:

1. **Conformal CQR expansion:** `p10 -= q_hat`, `p90 += q_hat`
2. **Safety interlock clamping** (monotonicity, bounds, feasibility)
3. **Monotonic floor enforcement:** `p10 = max(0, p10)`, `p50 = max(p10, p50)`, `p90 = max(p50, p90)`
4. **Wall-clock time conversion:** delay minutes added to scheduled arrival time → human-readable `HH:MM` strings
5. **Color coding:** green (≤15 min), amber (15–60 min), red (>60 min)

### 7.7 Cascade Simulator — `engine/simulator.py`

Uses **SimPy** discrete-event simulation with `simpy.PriorityResource` for section blocks:

- Rajdhani (priority 1) pre-empts Mail/Passenger (priority 4) on single-line sections
- Simulates: `CROSSING_HOLD`, `TSR` (Temporary Speed Restriction), `EXT_DWELL`, `RAKE_INHERIT`, `PLATFORM_WAIT`
- All delay minutes logged with exact causation to `sim_ledger` table
- `get_train_autopsy()` provides 100% attributed causal breakdown

## Gaps & Next Steps

### 1. No Experiment Tracking
No **Weights & Biases**, **MLflow**, or **Neptune** integration is present. Training metrics are written only to `ml/artifacts/manifest.json` and `ml/artifacts/metrics.json` (local JSON files). As dataset volume grows, tracking training runs becomes essential.

### 2. No Learning Rate Scheduler (GRU)
The PyTorch GRU trainer (`ml/model_seq.py`) uses a fixed Adam learning rate with no `ReduceLROnPlateau`, `CosineAnnealing`, or warmup schedule. Adding one could improve convergence.

### 3. No Gradient Clipping (GRU)
The GRU training loop does not apply `torch.nn.utils.clip_grad_norm_()`. This may cause instability on sequences with large delay spikes.

### 4. No Mixed Precision (AMP)
The GRU training does not use `torch.cuda.amp.autocast()`. For GPU training, enabling `torch.compile()` or AMP would significantly speed up training.

### 5. No Early Stopping
Both the LightGBM and GRU training loops run for a fixed number of iterations/epochs with no validation-loss-based early stopping. LightGBM supports `early_stopping_rounds` natively; the GRU would need a validation DataLoader.

### 6. Delta Model Composition Approximation
For `hops > 3`, the Delta models predict a single section delta and multiply by `hops`:
```python
p50 = current_delay + (delta_50 * hops)
```
This approximation assumes constant per-section delay across all hops, which ignores section-level heterogeneity. A multi-step autoregressive composition would be more accurate.

### 7. No Dockerfile / Container Setup
There is no `Dockerfile` or `docker-compose.yml`. Containerizing the Python API and Next.js frontend would simplify deployment and make the environment fully reproducible.

### 8. RAPIDAPI_KEY Required for Live Data
Without `RAPIDAPI_KEY` set in `.env`, the system always falls back to `MockReplaySource`. The scrape adapter (`collector/adapters/scrape.py`) is present but depends on external webpage layout consistency.

### 9. No Deployment Script
There is no `Makefile`, `deploy.sh`, or automated cloud deployment script. Workflows may need to be created for automated collection and retraining.

### 10. Holiday Calendar Not Implemented
Feature `day_type` is set to `0` (weekday) or `1` (weekend), but the value `2` (holiday) is defined in `features.py` and never actually assigned in `snapshots.py`. A proper Indian public holiday calendar lookup is missing.

### 11. Frontend API Integration Verification
The API polling logic in the Next.js dashboard should be regularly checked against updated backend schema definitions to confirm all 10 `/v1/` endpoints are seamlessly consumed.

### 12. Conformal Calibration Scope
`conformal_q_hat` is currently computed for the Direct LightGBM models. No separate CQR calibration exists for the Delta models or the PyTorch GRU challenger. Confidence bands for long-horizon predictions (>3 hops) rely on direct composition adjustments rather than independent split calibration.
